# deckdock/1: compiled deck format

`deckdock/1` is the format a deck is compiled to. It is the contract between
compilers (any tool that produces it), the checker (`deckdock check`), a future hub and a
future Anki add-on. Machine-readable parts: [`deckdock-1.schema.json`](deckdock-1.schema.json)
(structure only) and [`examples/`](examples/) (`valid/` and `invalid/`).

## Layout

One file per **edition** (a language or a variant of the same deck), with its media next to it:

```
dist/
  fr/
    deck.json
    media/
      carte-bordeaux.png
  en/
    deck.json
    media/...
```

`deck.json` is UTF-8 JSON. Every `deck.json` is checked independently.

## Publishing layout (optional)

A deck can be served from any HTTPS base URL (`<base>`) so that clients can subscribe to it. For a GitHub repository, the template publishes the content of `dist/` at the root of the `dist` branch, so `<base>` is `https://raw.githubusercontent.com/<owner>/<repo>/dist`. In the layout below `<base>` has no trailing slash; a custom base URL given to the add-on must end with `/`.

```
<base>/index.json
<base>/<edition>/deck.json
<base>/<edition>/media/<filename>
```

`index.json` lists the editions so a client can offer a choice without downloading every deck. It is UTF-8 JSON with these keys:

- `format` (required): the string `deckdock-index/1`;
- `editions` (required): an array, sorted by `edition`, of objects with `edition` (the edition code, string), `name` (string), `language` (array of strings) and `version` (string), copied from the `deck` object of `<edition>/deck.json`.

Clients read media by filename, percent-encoded in the URL (a file named `a b.png` is fetched from `<base>/<edition>/media/a%20b.png`).

## Objects

In **strict** mode (producers, `deckdock check`), unknown keys are rejected in every object, to catch typos; consumers validate in non-strict mode and ignore them (see [Compatibility](#compatibility)). "Required" means the key must be present.

### Top level

| Key | Type | Required | Rule |
| --- | --- | --- | --- |
| `format` | string | yes | Exactly `"deckdock/1"`. |
| `deck` | object | yes | See below. |
| `notetypes` | list of notetype | yes | |
| `notes` | list of note | yes | At most 50 000 notes. |
| `media` | list of media | yes | May be empty. |

### `deck`

| Key | Type | Required | Rule |
| --- | --- | --- | --- |
| `id` | string | yes | Slug matching `^[a-z0-9]+(?:-[a-z0-9]+)*$`. Chosen by the author, stable forever. |
| `edition` | string | yes | Non-empty, not `.` or `..`, no `/` or `\`. Free slug (`fr`, `en`, `bilingual`, `n2`...). It names the edition directory, and `deckdock check` requires it to equal that directory's name. |
| `name` | string | yes | Display name of the root deck. |
| `language` | list of string | yes | Non-empty list of BCP-47 codes: `["fr"]`, or `["fr", "en"]` for a bilingual edition. |
| `version` | string | yes | Opaque string generated by CI (ISO date + short commit sha), or `"dev"`. |
| `description` | string | no | Short Markdown. |
| `homepage` | string | no | |
| `license` | string | no | |
| `generator` | string | no | For example `"deckdock 0.1.0"`. |
| `anki_id` | integer | no | 1 to 2^63-1 (9223372036854775807). See "Attaching to an existing deck". |
| `options` | object | no | Study preset. Only `new_per_day` and `reviews_per_day` (integers >= 0). |

### `notetypes[]`

| Key | Type | Required | Rule |
| --- | --- | --- | --- |
| `id` | string | yes | Non-empty, unique in the file. Stable slug local to the deck. |
| `name` | string | yes | Anki notetype name. |
| `kind` | string | yes | `"standard"` or `"cloze"`. |
| `fields` | list of string | yes | Non-empty. Names are non-empty and unique. Their order is the field order. |
| `templates` | list of template | yes | Non-empty. A `cloze` notetype has exactly one template. |
| `css` | string | yes | |
| `anki_id` | integer | no | 1 to 2^63-1 (9223372036854775807). See "Attaching to an existing deck". |

Each template has the required string keys `name`, `front` and `back`. Templates use the Anki
syntax (`{{Field}}`, `{{cloze:Text}}`, `{{FrontSide}}`). JavaScript is allowed in templates.

### `notes[]`

| Key | Type | Required | Rule |
| --- | --- | --- | --- |
| `guid` | string | yes | Non-empty, unique in the file, stable across versions. |
| `notetype` | string | yes | Must be the `id` of a notetype of the file. |
| `deck` | string | yes | Sub-deck path relative to the root deck. `""` is the root, otherwise non-empty segments separated by `::`. |
| `fields` | object | yes | Keys are exactly the notetype's fields; values are HTML strings. |
| `tags` | list of string | yes | Each tag is non-empty and contains no whitespace. |

Field values are HTML: Markdown and other sources are already rendered by the compiler.

### `media[]`

| Key | Type | Required | Rule |
| --- | --- | --- | --- |
| `filename` | string | yes | Non-empty, no `/`, no `\`, not `.` or `..`. Unique in the edition. |
| `sha256` | string | yes | 64 lowercase hexadecimal characters. |
| `size` | integer | yes | Bytes, >= 0 and at most 10 485 760. |

## Identity and uniqueness

- (`deck.id`, `deck.edition`) identifies an update stream. Global uniqueness (owner prefix, etc.) is assigned by the hub.
- `notes[].guid` is the Anki GUID (a compiler SHOULD derive it deterministically, for example from the deck id, a card id and the edition). It is unique **within a file** and must stay stable between versions: it is the update key, and keeping it preserves scheduling. The same GUID may appear in several editions of the same deck. In an Anki collection a GUID is globally unique, so the add-on must prevent subscribing to two editions that share GUIDs, or offer to switch from one to the other.
- `notetypes[].id` is a stable slug local to the deck. Numeric Anki ids are derived by the add-on unless `anki_id` is given.
- `deck.version` is opaque; ordering of versions is the hub's business (order of receipt).

## Media and references

- Every file referenced from a field, a template or the CSS must be listed in `media`, and every listed file must exist in the edition's `media/` directory with the listed `size` and `sha256`. A file in `media/` that is not listed is an error.
- Referenced names are found with these patterns: `src="X"`, `src='X'`, `[sound:X]` and `url(X)` (quotes optional; `src` and `url` are matched case-insensitively). Each extracted name is HTML-unescaped (`&amp;` becomes `&`) and then percent-decoded (`%20` becomes a space) before it is compared with the listed filenames, so `src="a&amp;b.png"` and `src="a%20b.png"` refer to `a&b.png` and `a b.png`. A name is ignored when it contains `://`, starts with `/` (including protocol-relative `//`) or `data:`, or contains a `{{` template tag.
- Anki's media folder is flat, so a reference must be a bare filename. Any other relative reference containing `/` (for example `src="media/hello.png"`) is an error: "media references must be bare filenames".
- `sha256` is used for deduplication and verification.

## Limits (v1)

| Limit | Value |
| --- | --- |
| Notes per edition | 50 000 |
| Size of one media file | 10 485 760 bytes (10 MiB) |
| Total media per edition | 524 288 000 bytes (500 MiB) |

These are initial guard rails and may be adjusted.

## Attaching to an existing deck (`anki_id`)

`deck.anki_id` and `notetypes[].anki_id` are optional integers between 1 and 2^63-1 (Anki ids are signed 64-bit integers). When present, the add-on reuses exactly that Anki root deck and notetype, so decks already installed from an `.apkg` (fixed genanki ids) can be adopted without changing notetype. The notetype `name` and field names must then match the existing ones. Without them, the add-on derives ids deterministically.

`deck.options` is an optional study preset applied only on first installation and never overwritten afterwards.

## Validation

The JSON Schema encodes the **structural** rules only (it always forbids unknown keys, i.e. it describes strict mode): keys, types, `additionalProperties: false`, patterns, sizes of single values. These rules need the checker (`deckdock check`):

- uniqueness of `guid`, notetype `id` and media `filename`;
- note `fields` matching the notetype's fields, and `notetype` existing;
- the total media size;
- media files on disk (presence, size, sha256), unlisted files, and media references.

`deckdock check [DIST]` (default `dist`) checks every `<DIST>/<edition>/deck.json`, prints one error per line as `<path>: <JSON path>: <message>` (for example `dist/fr/deck.json: notes[3].fields: missing field 'Back'`) and exits with 1 if there is any error, 0 otherwise.

## Writing your own compiler

Any language or tool can produce `deckdock/1`: the format is plain JSON plus a `media/` folder. A compiler:

- **MUST** give every note a GUID that is unique within its file and stable across versions (it is the update key);
- **MUST** keep `deck.id`, edition codes, `notetypes[].id` and any source ids its GUIDs derive from (for example card ids) permanent, since changing one resets the users' review history;
- **MUST** use flat media filenames (no `/`, no `\`);
- **MUST** produce output that passes `deckdock check` in strict mode;
- **SHOULD** write `dist/<edition>/deck.json` as UTF-8 with `ensure_ascii=False`, with media in `dist/<edition>/media/`.

### Changing a published notetype

Subscribers already have your notetypes in their Anki collection, so changes to a published notetype fall into three groups:

| Change | Effect on subscribers |
| --- | --- |
| Note content (fields' values, tags), adding or retiring notes, template text, CSS | Applied normally; review history is kept |
| Adding a field **at the end** of `fields` | Changes Anki's schema: applying it requires a full AnkiWeb sync, so clients **MUST** ask the user to confirm (and to sync their other devices first). Reviews not yet synced from other devices can be lost |
| Removing, renaming or reordering fields; adding or removing templates; changing `kind` | **Not supported** by current clients: the update is refused and subscribers stay on the previous version. Removing a template would delete its cards and their review history, and a rename is indistinguishable from a removal plus an addition |

A compiler **SHOULD** therefore treat a published notetype's structure as frozen. To change it, prefer a new notetype (new `id`) for new notes.

In Python, the standard-library-only `deckdock` package helps: `deckdock.format` provides `TypedDict` models of this format (`CompiledDeck`, `Deck`, `DeckOptions`, `Notetype`, `Template`, `Note`, `MediaEntry`) and the reference checker, and `deckdock.guid.guid_for` derives GUIDs the way genanki does.

```python
from pathlib import Path

from deckdock.format import CompiledDeck, check_deck, check_dist
from deckdock.guid import guid_for

deck: CompiledDeck = {...}  # built with these models; use guid_for(...) for note GUIDs
assert check_deck(deck) == []
# write dist/<edition>/deck.json and dist/<edition>/media/, then:
assert check_dist(Path("dist")) == []  # same as `deckdock check dist`
```

The models describe the structure only; the rules above (slugs, uniqueness, limits, media) are enforced by `check_deck` and `check_dist`.

[deckdock-template](https://github.com/NayanChauveau/deckdock-template) is a complete example compiler (YAML cards to `deckdock/1`).

## Compatibility

`format` carries the major version. Adding an optional key stays in `deckdock/1`; a breaking change becomes `deckdock/2`. Consumers must reject a `format` they do not know.

Unknown keys are handled by validation mode. Producers (compilers, `deckdock check`) validate in **strict** mode, which rejects unknown keys to catch typos. Consumers (the hub, the add-on) **MUST** validate in **non-strict** mode (`strict=False` in the reference checker), which ignores unknown keys so that optional additions to `deckdock/1` do not break older consumers, while still enforcing every other rule.

## Example

```json
{
  "format": "deckdock/1",
  "deck": {
    "id": "hello-deck",
    "edition": "en",
    "name": "My first deck",
    "language": ["en"],
    "version": "dev"
  },
  "notetypes": [
    {
      "id": "basic",
      "name": "DeckDock Basic",
      "kind": "standard",
      "fields": ["Front", "Back"],
      "templates": [
        { "name": "Card 1", "front": "{{Front}}", "back": "{{FrontSide}}<hr id=\"answer\">{{Back}}" }
      ],
      "css": ".card { font-family: sans-serif; }"
    }
  ],
  "notes": [
    {
      "guid": "a1B2c3D4e5",
      "notetype": "basic",
      "deck": "",
      "fields": { "Front": "<p>Hello</p>", "Back": "<p>World</p>" },
      "tags": []
    }
  ],
  "media": []
}
```

More: [`examples/valid/full.json`](examples/valid/full.json) uses four notetypes (basic, reversed, cloze, mcq), sub-decks, `anki_id`, `options` and media.
